## 1. 前提整理（事実を揃える）

論点を議論する前に、事実として押さえておくもの。「わからない」まま議論すると決め直しになるので先に集める。

| # | 揃えること | 具体的に | 確認方法 |
|---|-----------|---------|---------|
| 1-1 | 目標指標の確定版 | スライドの指標のうち、イベント登録フォームで取るべき範囲。「場」の定義（オンライン/オフライン、一人完結は除く）の確定文言 | 指標を定めたオーナーに確認 |
| 1-2 | 現行フォームの利用実態 | 月間申請数、種類別（サポーター限定/一般公開/街頭）の内訳、主催別の内訳、却下・差し戻しの件数と理由 | 回答シートを集計 |
| 1-3 | 「困りごと」の実例 | 日付未定で相談したかった申請、議員参加希望の申請、外部イベントを載せたいと言われた件、がそれぞれ過去どのくらいあったか | 回答シートの特記事項欄・Slackの申請チャンネルを遡る |
| 1-4 | カレンダーの利用実態 | 購読者数、誰が見ているか（サポーター/本部/一般）、一般向けカレンダーを欲しいと言ったのは誰で、何に使いたいのか | カレンダー共有設定、要望者にヒアリング |
| 1-5 | 現行の承認運用 | 承認担当（運営側・サポーター側それぞれ）、承認基準、承認までの平均時間、差し戻しの基準 | 担当者にヒアリング |
| 1-6 | 現行の技術的制約 | Googleフォームの制約（条件付き必須ができない、質問追加でシート列が末尾に増える）、GASの脆い点（列番号固定、質問タイトル依存、本番でしか試せない） | タスク一覧 §1.3 に整理済み |
| 1-7 | 既存のルール文書 | 入力ガイドライン、共催ルール（他政党NG）、議員参加のポリシー、ブランド表現ルール（「チームみらい」名称の使用制限） | 文書の所在と最新版を確認 |
| 1-8 | 関連する他の取り組み | アクションボードの「イベントに参加しよう」「イベント運営を手伝おう」ミッション、サポーター向けLINE/オープンチャットでのイベント告知、との役割分担 | 各担当に確認 |

## 2. 論点整理（決めること）

要望ごとに「決めないと先に進めないこと」を列挙。推奨案はタスク一覧 §2 にあるが、ここでは**問いの形**で並べる。

### A. 指標取得（R1: 優先度 高）

| # | 論点 | なぜ決める必要があるか |
|---|------|---------------------|
| A-1 | 「デジタル民主主義を実践する場」に該当するかを、誰がどう判定するか（主催者の自己申告 / 本部判定 / 両方） | 判定基準がぶれると北極星の数値が信用できなくなる |
| A-2 | 登録時に取る項目をどこまで増やすか | 項目が増えると登録の離脱が増える。「指標に効く最小限」の線引きが必要 |
| A-3 | 街頭活動を「場」に含めるか | 一方向の活動は北極星の定義上は対象外だが、外輪アクションとしては数えたい可能性がある |
| A-4 | 2回目参加率・紹介率のように、登録時には取れない指標をどう扱うか（事後報告で取る / 別の仕組みで取る / 今は諦める） | 取れない指標を無理にフォームに入れると形骸化する |

### B. 事後報告（R2: 優先度 中）

| # | 論点 | なぜ決める必要があるか |
|---|------|---------------------|
| B-1 | 任意にした場合、どの程度の回収率を見込むか。回収率が低いときに指標として使えるか | 回収率次第で「のべ参加人数」の精度が決まる |
| B-2 | 報告依頼をどこに送るか（メール / Slack / 両方） | 主催者名がSlack表示名のため、Slackでの特定が不安定 |
| B-3 | 報告してもらった意見・数値を、誰がどう活用して主催者に返すか | スライドの「返答までの日数」指標に直結する。返さないなら報告してもらう意味が薄い |

### C. 一般公開カレンダー（R3: 優先度 中）

| # | 論点 | なぜ決める必要があるか |
|---|------|---------------------|
| C-1 | 誰に向けて公開するか（一般市民 / メディア / サポーター候補）、どこに掲載するか（Webサイト埋め込み等） | 公開範囲によってカレンダーの公開設定と掲載内容の基準が変わる |
| C-2 | 街頭活動を一般公開カレンダーに載せるか | 一般の人が「見に行ける」情報かどうか。警察への届け出状況が未確定なものを公開してよいか |
| C-3 | 公開カレンダーに載せる情報の範囲（主催者名を出すか、オンラインURLを出すか） | サポーター主催者の個人名を一般公開してよいかは本人同意が必要 |

### D. 主催区分（R4: 優先度 高・小）

| # | 論点 | なぜ決める必要があるか |
|---|------|---------------------|
| D-1 | 「党主催」の定義。本部主催のみか、支部・地域組織主催も含むか、議員事務所主催はどちらか | 通知先チャンネルと承認担当が主催区分で分かれるため |
| D-2 | 過去の「議員主催」データを集計上どう扱うか | 過去との比較が必要なら読み替えルールが要る |

### E. 日付未定申請（R5: 優先度 中）

| # | 論点 | なぜ決める必要があるか |
|---|------|---------------------|
| E-1 | 「議員ありきのイベントは原則開催しない」という党の方針と、日付未定の入口を作ることの整合。入口を作ること自体が「相談すれば議員を呼べる」というメッセージにならないか | 方針と仕組みが矛盾すると現場が混乱する |
| E-2 | 入口をどこに置くか（最初の分岐 / 各セクション内 / 特記事項） | 目立たせたくないが、見つからないと意味がない |
| E-3 | 日程確定後の流れ（再登録してもらう / 本部がシートを埋めて承認する） | 承認担当の作業負荷に直結する |

### F. 外部イベント（R6: 優先度 低・検討から）

| # | 論点 | なぜ決める必要があるか |
|---|------|---------------------|
| F-1 | そもそも受け付けるか | 受け付けないなら以降の論点は不要 |
| F-2 | 受け付ける場合の基準（テーマ、主催者の種類、他政党の扱い） | 「地元のお祭り」が混ざるのを防ぐ線引き |
| F-3 | 掲載内容の責任を誰が持つか（本部が内容を確認するか、情報提供扱いにするか） | 外部イベントのトラブル時に党の責任になりうる |
| F-4 | 既存カレンダーに混ぜるか、別カレンダーにするか | イベントだらけで本来の予定が埋もれる懸念 |

### G. 実現方法（R7: 優先度 高・最初に決める）

| # | 論点 | なぜ決める必要があるか |
|---|------|---------------------|
| G-1 | 既存フォームを直接改修するか、新フォームをstgとして作ってURL切替するか | 本番一体の構成では分岐変更を安全に試せない |
| G-2 | 当面Googleフォームを続けるか、将来アクションボード内にフォームを移す前提で設計するか | 移す前提なら、Googleフォーム側の作り込みを最小限にする判断になる |
| G-3 | 改善を一度に出すか、要望ごとに段階的に出すか | 承認担当・サポーターへの周知コストに影響する |

**2の完了条件**: 各論点について「決定 / 保留（理由と期限）」が記録されている。

## 3. 関係者確認

### 3.1 関係者マップ

### 3.2 確認の順番

依存関係があるので、この順で回すと手戻りが少ない。

1. **指標のオーナー**（A系）: ここが決まらないと取る項目が決まらない
2. **承認担当（両側）**（1-2、1-3、1-5、E-3、D-1）: 実態を把握し、運用負荷の上限を知る
3. **党本部・事務局**（E-1、D-1）: 日付未定入口の是非。NGなら R5 は取り下げ
4. **要望者ヒアリング**（C、F）: 一般公開カレンダーと外部イベントは要望の中身次第で設計が変わる
5. **広報・ブランド**（C-1、C-3、F-3）: 公開範囲の最終確認
6. **サポーター主催経験者**（A-2、B-1）: 設計案ができてからの反応確認
7. **メンテナー・開発チーム**（G系）: 実行方法の確定

### 3.3 持ち込む資料

- 1枚もの: 目的（北極星）、要望R1〜R7、各関係者に決めてほしい論点だけを抜粋したもの
- たたき台: タスク一覧 §4（登録時に取る項目案）、§5（事後報告案）、§7（日付未定案）
- 現行フォームのスクリーンショットまたは質問一覧

### 3.4 記録

関係者ごとの確認結果を「決定 / 保留 / 却下」で記録し、§2 の論点表に反映する。保留には理由と再確認の期限を書く。

**3の完了条件**: §2 の全論点に決定または保留（期限つき）が入っている。R5・R6 については「やる / やらない」が決まっている。

## 4. 実行方法の検討（関係者確認後）

ここは §2 G系の決定を受けて組む。詳細はタスク一覧のフェーズB・C・H。

- stg方式にする場合: コピーしたフォーム・別シート・別GAS・テスト用Slackチャンネル・テスト用カレンダーの準備
- GASの基盤改修（列番号固定の解消、イベントID採番）を機能追加の前に行う
- リリース順: R4（主催区分）→ R1（指標項目）→ R5（日付未定）→ R3（一般公開カレンダー）→ R2（事後報告）→ R6（外部イベント）
- 切替手順: Slack Events API のURL切替、旧フォームの受付停止、フォームURLの参照箇所の差し替え
