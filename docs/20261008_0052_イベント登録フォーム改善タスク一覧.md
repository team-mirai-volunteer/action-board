# イベント登録フォーム改善 タスク一覧

作成日: 2026-10-08
対象: 【チームみらい】イベント・街頭活動 登録フォーム（Googleフォーム）＋ 連携GAS ＋ Googleカレンダー

## 0. 背景と目的

組織活動の北極星は「**デジタル民主主義を実践する場ののべ参加人数**」（再訪率を条件とする）。
現在のイベント登録フォームは「カレンダー掲載と本部承認」が目的で設計されており、北極星や関連指標（初参加の人数・外輪経由の初参加数・2回目参加率・紹介率・サポーター主催の開催数 など）を計測するための情報を取得していない。

本ドキュメントは、以下の要望を実現するためのタスクを「検討 → 設計 → 実装 → 移行 → 運用」の順に洗い出したもの。

| # | 要望 | 優先度 |
|---|------|--------|
| R1 | 指標計測に必要な情報をイベント登録時に取得する（例: デジ民の実践につながるイベントか） | **高** |
| R2 | 開催後に通知を送り、実績を報告してもらう（任意） | 中 |
| R3 | 一般向けのみのカレンダーを追加する（登録フォームは1つのまま） | 中 |
| R4 | 「主催」の選択肢を「党主催 / サポーター主催」に変更する（議員主催を廃止） | 高（小） |
| R5 | 日付未定（議員ありき等）の申請入口を作る。カレンダー反映なし・Slack通知のみ | 中 |
| R6 | チームみらい主催以外の外部デジ民イベントも登録できるようにする | 低（検討から） |
| R7 | 既存フォーム改修 vs 新フォーム（stg運用→URL切替）の判断 | 高（最初に決める） |

既存機能（Slack通知・✅リアクションによる承認・カレンダー反映）は変えない前提。

## 1. 現状整理（前提の確認）

### 1.1 現在のフォーム構成

```
S1 共通: メール / 主催者名(Slack表示名) / 主催 / 登録の種類
  ├ S2 サポーター限定イベント（承認不要・即カレンダー）
  ├ S3 一般公開イベント（本部承認後カレンダー）
  └ S4 街頭活動（本部承認後カレンダー）
S5 共通: その他特記事項 / 誓約事項
```

### 1.2 現在のGASの流れ

```
onFormSubmit
  ├ 回答を「質問タイトル → 値」の辞書化 → Slack通知（主催でチャンネル・担当者を切替）
  ├ サポーター限定: スプレッドシート最終行を COL 固定番号で読み → 即カレンダー登録
  └ それ以外:        Slack の ts をシートの SLACK_TS 列に保存
doPost (Slack Events API)
  └ ✅ (white_check_mark) リアクション → ts でシート行を特定 → カレンダー登録
```

### 1.3 既知の構造的リスク（改修時に影響する点）

| 項目 | 内容 | 影響 |
|------|------|------|
| COL 固定番号 | `getEventData` は列番号ベタ書き。質問の追加・削除で列構成が変わるとカレンダー登録が壊れる | フォーム改修のたびに手で `COL` を直す必要がある |
| 質問タイトル依存 | `sendSlackNotification` は質問タイトルをキーに参照。文言を変えるとSlack通知から項目が消える（エラーにならず静かに欠落） | 文言変更時の検知が難しい |
| `getLastRow()` 依存 | 同時送信があると別の回答の行を読む可能性 | 発生頻度は低いが、再送や事後報告連携で行IDが必要になる |
| トークンのハードコード | Slack Bot Token がスクリプト本文に記載 | 共有・コピー時に漏洩しやすい（後述 §9） |
| 本番でしか動作確認できない | フォーム・シート・GAS・Slack・カレンダーが本番一体 | 分岐を変える改修をぶっつけで行うことになる |

> 1.3 の内容が、R7「新フォームをstgとして作るべきか」の判断材料になる。

## 2. 論点（最初に決めること）

タスクに着手する前に、以下を本部・運営メンバーと合意する。推奨案を併記。

| # | 論点 | 選択肢 | 推奨 |
|---|------|--------|------|
| Q1 | 既存フォームを直接改修するか、新フォームをstgとして作るか | A: 既存改修 / B: 新フォーム＋URL切替 | **B**。理由: 分岐・列構成・GASの3点を同時に変えるため本番改修はリスクが高い。コピーしたフォーム＋別シート＋別GAS＋テスト用Slackチャンネル・テスト用カレンダーで検証してから切り替える |
| Q2 | 「デジ民の実践につながる場か」を誰が判定するか | A: 主催者の自己申告 / B: 内容（やること）を選ばせて本部が判定 / C: 両方 | **C**。自己申告だけだと基準がぶれる。「イベントで行うこと」を選択式で取り、本部が最終判定して集計列に記録する |
| Q3 | 事後報告の手段 | A: 別の報告フォーム（イベントIDを事前入力したURL） / B: 登録フォームの再利用 / C: Slackスレッドで返信 | **A**。集計しやすく、通知文にURLを入れるだけで済む |
| Q4 | 事後報告の通知先 | A: 登録メールアドレス宛メール / B: Slack DM（メールからユーザー検索） / C: Slackチャンネルでメンション | **A＋C**。メールは確実に届く。Slackは主催者名が表示名のため検索が不安定 |
| Q5 | 一般公開カレンダーの実現方法 | A: 新しいカレンダーを追加し、一般公開イベントは両方に登録 / B: 既存を一般向けにしてサポーター限定を別カレンダーへ | **A**。既存の購読者・GASを壊さない |
| Q6 | 街頭活動を一般公開カレンダーに載せるか | 載せる / 載せない / 街頭演説ありのみ載せる | 要相談。一般の人が「見に行ける」情報かどうかで判断 |
| Q7 | 外部イベントの受付基準 | 受け付けない / 本部承認制で受け付ける / 別カレンダーに分ける | **本部承認制＋別カレンダー（または別ラベル）**。「地元のお祭り」が混ざるのを防ぐため、テーマ基準（下記 §6）を明文化する |
| Q8 | 日付未定申請の入口 | A: 登録の種類に「日程未定・相談」を追加 / B: 各セクションの日時を任意化し「日程の状況」選択を追加 / C: 特記事項に書いてもらう | **B**。最初の分岐に出すほどではない、という要望に合致。日時を任意にする代わりに「日程の状況: 確定 / 未定（本部に相談したい）」を必須にして入力漏れを防ぐ |
| Q9 | 指標の集計先 | A: 回答シート上で集計 / B: 集計用シートをGASで生成 / C: 将来アクションボードに取り込む | 当面 **B**。将来 C（§10 参照） |
| Q10 | 「主催」の表記変更に伴う旧データの扱い | 旧「議員主催」行をどう集計するか | 「党主催」に読み替える（集計時のマッピングで対応） |

## 6. 外部イベント受付の基準（たたき台）

受け付ける場合の最低条件案。A-6 で決める。

- テーマが「デジタル民主主義の実践」に直接関係する（例: 市民参加・熟議・オープンガバメント・いどばた等のツール利用・政策対話）。地域の祭りや一般的な交流会は対象外
- 登録者はチームみらいのサポーターで、参考URL（主催団体の告知ページ）を必須にする
- 本部承認制（既存の✅フローを流用）。カレンダー上は【外部】ラベル、または外部イベント専用カレンダーに分けて既存カレンダーを汚さない
- 他政党主催のイベントは原則不可（既存の共催ルールと整合）
- 掲載は「情報提供」である旨をカレンダー説明文に明記（チームみらいの推薦・関与ではない）

## 7. 日付未定申請の設計（たたき台）

- 「登録の種類」の分岐は変えず、各セクションに **「日程の状況」（確定 / 未定・本部に相談したい）** を必須で追加し、開催日時（開始・終了）を任意にする
- 未定の場合は「希望時期」「相談したい内容（議員の参加希望など）」を記入してもらう。議員の参加希望は既存の「その他特記事項」の案内と統合する
- GAS: 未定なら【日程未定・相談】としてSlack通知のみ。カレンダー登録とSLACK_TS保存はしない
- 日程確定後は、(a) 再登録してもらう（シンプル）か、(b) 本部がシートの日時を埋めてから✅でカレンダー登録する（既存の `registerToCalendarFromSlack` はシートの行を読むため、SLACK_TS を保存しておけば追加実装なしで成立する）のどちらかを A-7 で決める
- 日時が空なのに「確定」が選ばれた回答は C-5 の警告で検知する

## 8. 推奨する進め方（順序）

1. **フェーズA（検討）** を1〜2週間で終える。特に Q1（stg方式）と §4 の項目確定が先
2. **フェーズB・C（基盤）** を先に行う。列固定の解消（C-1）とイベントID（C-3）がないと、以降の機能追加がすべて脆くなる
3. **フェーズD・E** で R4 → R1 → R5 → R3 の順に実装（効果が高く既存への影響が小さい順）
4. **フェーズH（移行）** でURL切替
5. **フェーズF（事後報告）・G（集計）** は切替後に追加しても既存機能に影響しないため、別リリースにしてよい
6. **R6（外部イベント）** は A-6 の判断後。受け付けないと決めた場合はタスクを削除する

## 9. セキュリティ上の注意

### 対応状況（2026-10-08）

| 項目 | 状況 |
|------|------|
| トークン・IDのスクリプトプロパティ化 | 完了 |
| 運営Slack側 Bot Token の再発行 | 完了 |

### 運用ルール

- 本ドキュメントや Issue、リポジトリにはトークン・チャンネルID・スプレッドシートID を記載しない
- GAS プロジェクトの共有範囲（編集者）を確認し、必要最小限にする
- GAS 内に `auth.revoke` を呼ぶ関数を常設しない（誤実行で通知が止まる）。必要なときだけ追加し、終わったら削除する

### Slack Bot Token 再発行の手順メモ（次回用）

1. 対象トークンで `auth.test` を呼び、`team` が想定のワークスペースであることを確認する
2. `auth.revoke` で無効化する。**再インストールだけではトークンは変わらない**（同じ値が返る）
3. api.slack.com/apps で該当アプリを「Reinstall to Workspace」し、新しい Bot User OAuth Token をスクリプトプロパティに貼り替える
4. 無効化するとボットが通知チャンネルから外れるため、チャンネルで `/invite @` の候補からボットを選んで追加し直す（「表示する」表示はワークスペースへの導入を示すだけで、チャンネル参加とは別）
5. テスト送信して `Slack API response` が `"ok":true` になることを確認する
6. 無効化〜復旧の間に届いた申請は Slack 通知に失敗し ts が保存されないため、回答シートを確認して手動対応する
