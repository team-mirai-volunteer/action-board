## 1. 背景・課題（要約）

チームみらいは、選挙で議席を得ることそのものを目指す政党ではない。目指しているのは**「デジタル民主主義の実現」**——市民が政治・社会活動に、選挙の有無にかかわらず日常的に参加し続けられる社会をつくること。選挙はそのための手段の一つに過ぎず、本質的に重要なのは平時から市民が関わり続けられる場をつくること自体にある。

次の国政選挙は2028年。選挙の圧力がない今の2年間は、「選挙がなくても人が関わり続けられる仕組み」を低コストで試し、失敗し、直せる期間でもある——という意味で今は好機だが、これは選挙対策として今やる理由ではなく、平時の参加の場という本来の目的にじっくり取り組める期間だと捉えている。

現状のアクションボードは選挙活動の記録用に作られた仕様が中心で、継続利用を促す仕組みが不足している。

| 指標 | 現状 |
|---|---|
| 翌月定着率（当月ミッション達成者のうち翌月も達成した割合） | **4%** |
| 月間アクティブ（2026年7月） | **282人**（ピーク時8,474人の3%） |
| 累計登録者のうち直近で動いていない割合 | **97%** |

登録後の落ち込みは「7日以内に初回ミッション達成：約45%」→「翌月も活動：4%」という1回きりで終わるフローに集約される。一方で、1回達成した人の定着率は約15%（全体の3〜4倍）、通知なしでも毎月80〜100人が自発的に復帰しているなど、**「もう1つ」につなげる導線さえ整えれば伸びる余地がある**、というのが今回のロードマップの前提。

原因と対応フェーズの対応関係：

- ミッションが選挙仕様のまま（72本中24本非表示、表示分の7割がフォロー・いいね系）→ **Phase 1**
- 継続利用を促す通知がない（LINE公式未連携、メールはウェルカム1通のみ）→ **Phase 2**
- サポーター向け情報がNotion等に分散し「アクションボードを開く理由」がない → **Phase 3**

## 2. 目指す姿

アクションボードを「たまにミッションをやる場所」から「これを見ればサポーター活動のすべてがわかる場所（サポーターポータル）」に変える。目指すのは選挙用の動員名簿ではなく、選挙の有無にかかわらず市民が政治・社会活動に参加し続けられる場そのもの。企画・要件定義・コンテンツは組織活動本部（湯田）が持ち、実装をClaude Codeとの壁打ちで進める。

目指す数値（2026年内・仮置き、Phaseごとに計測して見直す）：

- 翌月定着率：4% → 10%（中期で20%台）
- 登録後7日以内の初回ミッション達成率：45% → 60%
- 月間アクティブ：282人 → 1,000人

## 3. 進め方のルール

- **開発体制**：企画・要件定義・実装は湯田＋Claude Codeで自走。実装後、村井さん・志水さんに技術レビュー（品質・セキュリティ・既存コードとの整合性）を依頼する。
- **相談よりPR**：開発チームの意向として「途中で相談されるより、PRを見て変えたり提案する方がラク」。よって事前の設計相談は原則行わず、動くPRを小さく出してレビューで方向修正してもらう。設計判断が絡むPRは、説明文に設計意図・検討した代替案・自信のない箇所を明記してレビューの材料にする。
- **PRの単位**：機能ごとに小さく分割する。1 PR = 1機能追加/1改善を基本。新規テーブルを伴う機能は「マイグレーション＋ロジック」と「UI」を別PRに分け、差し戻し時の被害を小さくする。
- **CLAUDE.mdの必須ルールに従う**：worktree作成、Service層経由のDBアクセス、ミッション/シーズンのYAML管理、Supabaseクライアントの使い分け、認可はactions層で行う、push前のbiome/typecheck/testチェック、PRに`Resolves #issue番号`を記載、CodeRabbitレビューの確認、など。詳細は `CLAUDE.md` 本体を参照。
- **デザイン**：新規Canvas作成はしない。[既存のデザインシステム/Canvas](https://claude.ai/design/p/2a300789-1a0e-4f29-8893-6e06fbf24d63?via=share)にあるコンポーネント・トーンを流用する。ここにない新規UIパターンが必要になったときだけ最小限で拡張する。
- **法務確認が必要なもの**：メール・LINEの新規配信は配信同意の取得・配信停止導線の設置が必須。これは組織活動側（湯田）でPhase 2着手と並行して進める。

## 4. ロードマップ

各項目に「担当トラック」を付けている。

- 🟢 **ソロ実装**：湯田＋Claude CodeでPR作成まで完結できる想定（YAML編集、feature配下のUI/ロジック追加、Server Actions、DBマイグレーション含む）。設計の妥当性はPRレビューで判断してもらい、事前相談はしない。
- 🟠 **要・開発チーム連携**：開発チームしか持っていない情報・権限（外部サービスの契約状況、DNS、リポジトリ外のシステム）が必要で、PRを出すだけでは前に進められないもの。

想像による分類であり、実際に触ってみて判断が変わる箇所は都度この表を更新する。

### Phase 0｜計測 — 効果が測れる状態を先に作る（8/18週・半日〜1日）

このプロダクトには定着率・MAUを継続的に見る仕組みがない（トップページの `metrics` は公開用の累計カウンター）。一方、本番DBの `public` スキーマ全テーブルはBigQueryにレプリケーションされており（`bq_pub` / Datastream構成）、湯田はBigQueryへのアクセスを持っている。**アプリ側の実装ゼロで計測基盤が作れる**ため、施策より先にここを固める。定着率は月次指標で1ヶ月遅れて確定するので、ベースライン記録は今月から始めないと10月に効果を語れない。

| 項目 | トラック | メモ |
|---|---|---|
| KPI定点クエリの作成（定着率・MAU・7日以内初回達成率・ファネル） | 🟢 ソロ実装 | BigQuery上の `achievements` 等から算出。クエリは `docs/` にPR化し、算出ロジックを開発チームからも見える状態にする。 |
| モニタリングシートの自動更新 | 🟢 ソロ実装（アプリのコード変更なし） | BigQueryのScheduled Query＋スプレッドシート吐き出しで週次更新。チームに共有し、進捗報告はこのシートを見てもらう形にする。 |
| 施策別の成功指標の定義 | 🟢 ソロ実装 | 各機能に「何が動いたら成功か」を1指標ずつ紐付ける（例：診断完了率、達成後おすすめ経由の2回目達成率、ストリーク継続者数、お知らせ閲覧数）。 |

※Supabase本番へのアクセス付与は不要になった（BigQueryで足りる）。アプリ内KPIダッシュボードも当面作らず、スプレッドシートで運用する。

### Phase 1｜ミッションを「やりたくなる」形に整える（3〜4週間）

ファネル最大の穴＝「1回やって終わり」に直接効くものから順に出す。

| 項目 | トラック | メモ |
|---|---|---|
| ミッション体系の再整理（関わり方別の分類） | 🟢 ソロ実装 | `mission_data/missions.yaml` / `categories.yaml` / `category_links.yaml` の宣言的編集が中心。コード変更はUI表示側の軽微な調整程度。最初のPRとして最も低リスク。**実施案は[ミッション棚卸しと再分類案](./20260818_0315_ミッション棚卸しと再分類案.md)を参照**（継続48・復活12・選挙アーカイブ7・削除統合5、関わり方別6カテゴリ）。着手前に処遇案のレビューと要確認5件の解消が必要。 |
| 達成後の「次のおすすめミッション」表示 | 🟢 ソロ実装 | `mission-detail` / `missions` feature の拡張。DB変更なしで「1回やって終わり」に直撃する最小施策のため、順番を繰り上げ。 |
| お知らせ機能（Phase 2から前倒し） | 🟢 ソロ実装 | `announcements.yaml`＋CI同期（`missions.yaml` と同じ既存パターン）で管理し、投稿はPR経由。管理画面・権限設計・Supabaseアクセスがすべて不要になり、投稿内容にもレビューが入る。実装は表示UIのみ。「戻ってきたら新しい情報がある」状態を早く作る。 |
| トップ画面のUIレイアウト改善 | 🟢 ソロ実装 | 既存コンポーネントの並び替えが中心。 |
| 活動ストリーク（表示のみ） | 🟢 ソロ実装（2PRに分割） | 新規テーブル＋連続判定ロジック。JSTの日付境界・同日複数達成の扱いはバグりやすいためテストを厚めに書く。「マイグレーション＋判定ロジック」→「表示UI」の順で2PRに分け、設計意図はPR説明文に明記。**ボーナスXP・連続ランキングはPhase 2へ**（思い出させる通知がない状態で連続を要求しても機能しにくいため、通知とセットで出す）。 |
| 関わり方診断（3〜4問→おすすめミッション表示） | 🟢 ソロ実装 | 新規ウィザードUI＋推薦ロジック。DBスキーマ変更なし。既存の `onboarding` feature のパターンを踏襲。新規登録者にしか効かず月間新規は少ないため、Phase 1の最後に回す。 |
