- 参考：[開発チームMTG資料（アクションボードの改善 — 課題共有と開発協力のお願い）](https://claude.ai/code/artifact/92b4109f-3a09-4043-b676-3371f67f5520)

## 1. 背景・課題（要約）

チームみらいが目指す「デジタル民主主義の実現」には、選挙期間だけでなく平時から市民が関わり続ける場が必要。次の国政選挙は2028年で、選挙の圧力がない今の2年間が「選挙がなくても人が関わり続けられる仕組み」を低コストで試し、失敗し、直せる唯一の期間。

現状のアクションボードは選挙活動の記録用に作られた仕様が中心で、継続利用を促す仕組みが不足している。

| 指標 | 現状 |
|---|---|
| 翌月定着率（当月ミッション達成者のうち翌月も達成した割合） | **4%** |
| 月間アクティブ（2026年7月） | **282人**（ピーク時8,474人の3%） |
| 累計登録者のうち直近で動いていない割合 | **97%** |

登録後の落ち込みは「7日以内に初回ミッション達成：約45%」→「翌月も活動：4%」という1回きりで終わるフローに集約される。一方で、1回達成した人の定着率は約15%（全体の3〜4倍）、通知なしでも毎月80〜100人が自発的に復帰しているなど、**「もう1つ」につなげる導線さえ整えれば伸びる余地がある**、というのが今回のロードマップの前提。

原因と対応フェーズの対応関係：

- ミッションが選挙仕様のまま（72本中24本非表示、表示分の7割がフォロー・いいね系）→ **Phase 1**
- 継続利用を促す通知がない（LINE公式未連携、メールはウェルカム1通のみ）→ **Phase 2**
- サポーター向け情報がNotion等に分散し「アクションボードを開く理由」がない → **Phase 3**

## 2. 目指す姿

アクションボードを「たまにミッションをやる場所」から「これを見ればサポーター活動のすべてがわかる場所（サポーターポータル）」に変える。企画・要件定義・コンテンツは組織活動本部（湯田）が持ち、実装をClaude Codeとの壁打ちで進める。

目指す数値（2026年内・仮置き、Phaseごとに計測して見直す）：

- 翌月定着率：4% → 10%（中期で20%台）
- 登録後7日以内の初回ミッション達成率：45% → 60%
- 月間アクティブ：282人 → 1,000人

## 3. 進め方のルール

- **開発体制**：企画・要件定義・実装は湯田＋Claude Codeで自走。実装後、村井さん・志水さんに技術レビュー（品質・セキュリティ・既存コードとの整合性）を依頼する。事前相談なしでPRを作ってレビュー依頼する進め方も許容されている。
- **PRの単位**：機能ごとに小さく分割する。1 PR = 1機能追加/1改善を基本とし、大きくなりそうな場合は事前に村井さん・志水さんに方向性だけ相談する。
- **CLAUDE.mdの必須ルールに従う**：worktree作成、Service層経由のDBアクセス、ミッション/シーズンのYAML管理、Supabaseクライアントの使い分け、認可はactions層で行う、push前のbiome/typecheck/testチェック、PRに`Resolves #issue番号`を記載、CodeRabbitレビューの確認、など。詳細は `CLAUDE.md` 本体を参照。
- **デザイン**：新規Canvas作成はしない。[既存のデザインシステム/Canvas](https://claude.ai/design/p/2a300789-1a0e-4f29-8893-6e06fbf24d63?via=share)にあるコンポーネント・トーンを流用する。ここにない新規UIパターンが必要になったときだけ最小限で拡張する。
- **法務確認が必要なもの**：メール・LINEの新規配信は配信同意の取得・配信停止導線の設置が必須。これは組織活動側（湯田）でPhase 2着手と並行して進める。

## 4. ロードマップ

各項目に「担当トラック」を付けている。

- 🟢 **ソロ実装**：湯田＋Claude Codeで設計から実装・PR作成まで完結できる想定。既存アーキテクチャの範囲内（YAML編集、既存feature配下のUI/ロジック追加、Server Actions、DBマイグレーション含む）。実装後は通常どおり技術レビューを依頼する。
- 🟠 **要・開発チーム連携**：外部サービスとの新規契約・既存インフラの現状確認・アーキテクチャ判断・他システム（みらいいぬ等）連携が絡み、実装着手前に村井さん・志水さんへの確認や協力が要る想定。

想像による分類であり、実際に触ってみて判断が変わる箇所は都度この表を更新する。

### Phase 1｜ミッションを「やりたくなる」形に整える（3〜4週間）

| 項目 | トラック | メモ |
|---|---|---|
| ミッション体系の再整理（関わり方別の分類） | 🟢 ソロ実装 | `mission_data/missions.yaml` / `categories.yaml` / `category_links.yaml` の宣言的編集が中心。コード変更はUI表示側の軽微な調整程度。 |
| 関わり方診断（3〜4問→おすすめミッション表示） | 🟢 ソロ実装 | 新規ウィザードUI＋推薦ロジック。DBスキーマ変更なしで実装可能。既存の `onboarding` feature のパターンを踏襲。 |
| 達成後の「次のおすすめミッション」表示 | 🟢 ソロ実装 | `mission-detail` / `missions` feature の拡張。DB変更なし。 |
| 活動ストリーク＋連続ボーナス＋連続ランキング | 🟢 ソロ実装（マイグレーションのみレビュー必須） | 新規テーブルが必要（連続活動日数の記録）。湯田はSQLを書けるため設計・実装は可能。マイグレーション内容は村井さんに確認してもらう。 |
| トップ画面のUIレイアウト改善 | 🟢 ソロ実装 | 既存コンポーネントの並び替えが中心。 |

## 5. 次にやること

1. Phase 1の着手：ミッションYAMLの再整理（コンテンツ整理）から着手し、並行して診断UIの設計を進める。
2. Phase 1の最初の実装が固まり次第PRを作成し、村井さん・志水さんにレビューを依頼する。
3. ストリーク機能のマイグレーション設計を先に固め、着手前に村井さんに設計レベルで一度確認してもらう。
4. Phase 2着手前に、LINE公式アカウントの現状（権限・契約・Messaging API利用可否）を開発チームに確認する。
5. Phase 2着手と並行して、メール・LINE配信の法務確認（配信同意取得・配信停止導線）を組織活動側で進める。
6. 各Phaseリリース後、定着率・MAU等のKPIを計測し、本ドキュメントの数値目標・トラック分類を実態に合わせて更新する。
