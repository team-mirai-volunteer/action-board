# 非開発者中心の開発体制検討（壁打ちメモ）

作成日: 2026-08-07
ステータス: 検討中（実装前の論点整理）

## 背景と目的

これまで開発者が管理してきた action-board を、今後は非開発者であるユダさんを中心に開発を進める体制へ移行する。前提となる考え方は以下の通り。

- Claude と壁打ちしながら開発を進める
- プレビュー環境で実際の出来栄えを確認できるようにする
- そのために「権限付与」「AIレビュー」「Supabaseのブランチ分岐」の3要素を整備する

このドキュメントは、実装に着手する前に現状を調査し、各論点の選択肢と推奨案を整理したものである。

## 現状調査の結果（前提の確認）

検討の前に、リポジトリの現状を整理する。**想定と異なる点がいくつかある**ので先に共有したい。

| 項目 | 現状 |
|---|---|
| AIレビュー | **CodeRabbit が導入済み**（`.coderabbit.yaml`、auto_review 有効、draft PR もレビュー対象）。CodeRabbit は GPT 系モデルを使う SaaS なので、「GPT 系の AI レビュー」は実はすでに入っている |
| レビュー観点の定義 | `docs/review-rules.md` と `reviewrules.toml` に観点が整備済み。CodeRabbit は `docs/*.md` と CLAUDE.md をガイドラインとして学習する設定 |
| デプロイ | `develop` → staging、`main` → production。GitHub Actions がマイグレーション適用 + データ同期後、Vercel の Deploy Hook を叩く（`.github/workflows/deploy.yml`） |
| Supabase | staging / production の **2プロジェクト構成**。ブランチング（Preview Branch）は未導入 |
| Supabase 設定 | `supabase/config.toml` が checked-in されており、deploy 時に `supabase config push` される。**設定はすでにコードで宣言的に管理されている** |
| 公開スキーマ | `config.toml` の `[api] schemas = ["public", "graphql_public"]`。マイグレーション内に独自スキーマの作成は見当たらない |
| ライセンス | **AGPL-3.0 + CLA**（`LICENSE`、`CLA.md`） |
| Vercel | `vercel.json` で main / develop の Git 連携デプロイを無効化（Deploy Hook 経由に一本化）。それ以外のブランチの Preview Deployment 設定は Vercel ダッシュボード側の状態に依存（要確認） |

## 論点1: ユダさんへの開発者権限の付与

### 推奨

**GitHub は org の team 経由で Write（write）権限を付与する。Admin は不要。** あわせてブランチ保護を「人が直接 push できない」前提で固める。

必要な権限のフルセットは GitHub だけではない点に注意。

| 対象 | 付与する権限 | 目的 |
|---|---|---|
| GitHub リポジトリ | Write（team 経由） | ブランチ push / PR 作成。**フォークではなく本体ブランチから PR を出せる**ことが後述の AI レビュー・プレビューの前提になる |
| Vercel | Member（Viewer でも可） | Preview Deployment の URL 確認、ビルドログ閲覧 |
| Supabase | staging プロジェクトの**最小権限ロール**（Team プラン以上なら Read-only、なければ Developer をプロジェクトスコープで付与） | Preview Branch の状態確認、ログ閲覧。注意: Supabase の Developer ロールは**データ・Storage の変更まで可能**なので、閲覧目的なら Read-only が望ましい。staging に実データ・個人情報が含まれるかどうかも権限判断の前提として確認する。**production は原則付与しない**（事故防止。必要になったら Read-only） |
| Claude Code | このリポジトリをスコープに含む環境 | 壁打ち・実装の主戦場 |

### セーフティネット（権限より重要）

非開発者中心の運用では「間違えても壊れない」構造が権限設計の本体になる。

- `main` / `develop` のブランチ保護: 直接 push 禁止、PR 必須、**required status checks** を必須化、approving review 1件以上を必須化。required checks には**実際の PR 用ジョブ名をそのまま登録する**（例: `Check code with Biome and tsc`、`Supabase & Integration Tests`、`E2E Tests`、`Check Supabase generated types` など。名前がズレると保護が効かない）。なお `deploy.yml` は push トリガーのため PR のゲートには含められない
- production への経路は今まで通り `main` へのマージのみ。マージ権限を持つ人（開発者側のレビュアー）を明確にする
- CODEOWNERS を置いて、マイグレーション（`supabase/migrations/`）や CI（`.github/workflows/`）など影響の大きいパスは開発者のレビューを必須にする、という段階的な守り方も可能

## 論点2: AIレビューの導入（→ 実際は「強化」）

### 現状認識

CodeRabbit がすでに動いており、モデル多様性（Claude で書いて GPT 系がレビューする）という当初の目的は**現時点で満たされている**。よって新規構築ではなく、非開発者中心の運用に耐えるようチューニングするのが本筋。

### 強化案

1. **`profile: "chill"` → `"assertive"` に変更**: 現状は指摘を控えめにする設定。書き手が非開発者になるなら、細かい指摘もAIに拾わせて人間レビュアーの負荷を下げる方が合う
2. **request_changes ワークフローの有効化**: `.coderabbit.yaml` に `request_changes_workflow: true` を設定すると、CodeRabbit が formal review（Changes Requested / Approved）を出すようになり、ブランチ保護の required approving review と連動してマージをブロックできる（現状は未設定でコメントのみ）。status check ベースでブロックしたい場合は CodeRabbit の pre-merge checks を使う
3. **セカンドオピニオンの追加（任意）**: レビュアーをもう1系統増やすなら候補は以下。認証方式と必要な秘密情報は候補ごとに異なる

| 候補 | モデル系統 | 認証方式 / 必要な秘密情報 | 公開リポジトリでの費用 | 備考 |
|---|---|---|---|---|
| CodeRabbit（導入済み） | GPT 系 | GitHub App（リポジトリに secrets 不要） | **OSS 向けプランで無料**（公開リポジトリが前提） | 現行。設定資産あり |
| Gemini Code Assist for GitHub | Gemini | GitHub App（リポジトリに secrets 不要） | 無料 | `GEMINI.md` が既にあり親和性あり |
| OpenAI Codex レビュー | GPT 系 | GitHub 連携（ChatGPT アカウント紐付け） | ChatGPT プラン依存 | CodeRabbit と系統が重複 |
| Claude Code GitHub Actions | Claude | GitHub Actions。通常は `ANTHROPIC_API_KEY` または `CLAUDE_CODE_OAUTH_TOKEN` を **Actions Secrets に登録**する必要あり。OIDC（Workload Identity Federation）を使えば静的キーなしにできる | API 従量 | 書き手と同系統のため「多様性」目的には不向き。修正の自動化用途なら有用 |

### API キー秘匿の懸念について（重要な訂正）

「オープンソースだと AI レビュアーの API キーを隠すのが煩雑」という懸念は、**大部分が杞憂**である。ただしリスクの所在は正確に区別しておく。

- CodeRabbit や Gemini Code Assist は **GitHub App** として動くため、キーはベンダー側にあり、リポジトリには設定ファイル（公開して問題ないもの）しか置かない
- 自前の GitHub Actions で API を叩く場合も、**GitHub Actions Secrets は公開リポジトリでも秘匿される**。ログにも自動マスクされる
- **フォークからの PR**: フォーク発の `pull_request` イベントには secrets が渡らず、`GITHUB_TOKEN` も read-only に落ちる（保護機構であり、漏洩リスクではない）。ユダさんは Write 権限を持ち本体ブランチから PR を出すので、この制約に当たらない
- **本体ブランチ側のリスク**: このリポジトリは `deploy.yml` や schedule 駆動のワークフローが push 時に secrets を使う。同一リポジトリのワークフロー改変や依存パッケージ経由の持ち出しに対しては、ログの自動マスクだけでは防げない。対策は「公開/非公開」ではなく、**`GITHUB_TOKEN` の permissions 最小化、production/staging secrets を Environment（承認付き）に限定する現行構成の維持、可能な箇所は短期 OIDC 認証へ移行**という運用面で行う（この点は非公開リポジトリでも同様に必要）
- やってはいけないのは、フォーク PR に secrets を渡すために `pull_request_target` で checkout する構成のみ。これを避ければ安全

## 論点3: Supabase のブランチごとの分岐

### 仕組みと導入方針

Supabase Branching（Preview Branch）を **staging プロジェクトに対して**導入する。PR 作成時に staging から Preview Branch がフォークされ、`supabase/migrations/` と `config.toml` がそのブランチに自動適用される。Vercel 連携を有効にすると、Preview Deployment に**そのブランチ専用の `SUPABASE_URL` / `ANON_KEY` が自動注入**される。

これで「PR ごとに DB スキーマ変更込みのフルスタックプレビュー」が成立し、ユダさんの確認フローは「PR の Preview URL を開くだけ」になる。

**適用範囲の切り分け（重複適用の防止）**: Supabase の GitHub 連携は Git ブランチと Preview Branch を対応させてマイグレーション・config を自動適用するため、既存の `deploy.yml`（`develop` / `main` への push で `supabase db push` + `supabase config push` を実行）と適用経路が重複しうる。導入時は **GitHub 連携の適用対象を PR の Preview Branch のみに限定**し、staging 本体（develop）と production（main）へのマイグレーション適用は現行どおり `deploy.yml` を唯一の経路として維持する。Vercel 側も同様に、`vercel.json` で main / develop の auto deploy を無効化し Deploy Hook に一本化している現行構成を維持したうえで、PR ブランチの Preview Deployment にのみ branch credentials が同期されることを確認する（Supabase 側が変数同期後に最新デプロイを再トリガーする仕様のため、順序の問題は基本的に自動処理される）。

### 「スキーマを都度パブリックにする手間」への回答

懸念されていた「ブランチごとに都度スキーマを公開設定しないと動かない」問題は、**`supabase/config.toml` の `[api] schemas` に宣言すれば解消する**。

- Preview Branch は作成時にリポジトリの `config.toml` を自動適用するため、そこに列挙されたスキーマは**全ブランチで自動的に公開される**。ダッシュボードでの都度設定は不要になる
- 「DB 上の公開可能なスキーマをすべて自動で公開する」機能自体は存在しない（内部スキーマの誤露出を防ぐため意図的にホワイトリスト方式）。ただし宣言は一度きりで済むので、運用上の手間はほぼゼロになる
- なお現在のマイグレーションには独自スキーマの作成が見当たらず、`config.toml` も `public` + `graphql_public` のみ。**過去にこの手間が発生したのは、ダッシュボード上で手動追加した公開スキーマが config に反映されていなかったケースではないか**。心当たりのあるスキーマ名があれば `config.toml` に追記して解消しておきたい（→ 確認事項へ）

### 導入時の実務的な論点

1. **プラン・コスト**: Branching は Pro プラン以上が必要。Preview Branch は固定月額ではなく**使用量課金**で、compute（Micro Compute で 1ブランチ・1時間あたり $0.01344。常時稼働なら月 $10 弱に相当）に加えて egress / disk storage も課金対象になる。**Spend Cap の対象外**なので、上限設定に頼らず、PR クローズで自動削除する運用と Spending 監視（同時ブランチ数・稼働時間のアラート）でコストを管理する
2. **シードデータ**: Preview Branch はマイグレーション + `seed.sql` を流すが、ミッション等のデータは `mission:sync` 系の独自スクリプト依存。ブランチ作成時に GitHub Actions で `mission:sync` / `season:sync` / `posting:sync` を Preview Branch に向けて実行するステップの追加が必要（これがないと「画面は開けるがミッションが空」のプレビューになる）
3. **認証系の制約**: LINE ログインはコールバック URL の事前登録が必要で、動的な Preview URL をワイルドカード登録できない。**プレビューでは認証込みのフローが完全には動かない可能性が高い**。対策候補: (a) プレビューでは Email 認証のみ許可、(b) 検証用の固定ドメインを 1 つ用意して主要検証に使う、(c) 認証不要ページ中心の確認と割り切る
4. **Vercel 側の確認**: 現在 PR ブランチの Preview Deployment が有効かどうかはダッシュボード確認が必要（`vercel.json` は main / develop の無効化のみ）。無効なら有効化する

## 論点4: リポジトリの非公開化

### 推奨: **公開のまま維持する**

非公開化の動機だった「API キー秘匿」は論点2の通り技術的に解決済みのため、非公開化は目的に対して過剰な手段になる。さらに非公開化には以下の実コストがある。

- **CodeRabbit の OSS 向け無料プランを失う**（OSS プランは公開リポジトリ限定。非公開化すると有料プランへ移行、シート課金）
- **GitHub Actions の無料枠を失う**（公開リポジトリは standard runner 無制限無料。非公開はプランの月間無料分を消費し、超過は分数課金。このリポジトリは CI が重いので影響が大きい）
- **AGPL-3.0 / フォークの性質**（既存公開物と今後の開発を分けて考える）:
  - **既存公開物**: これまでに公開されたコミットや既存の公開フォークは回収できない。GitHub の仕様上、リポジトリを非公開化しても既存の公開フォークは切り離されて公開のまま残る
  - **今後の開発**: AGPL 自体は private use を許容しており、非公開で開発を続けること自体はライセンス違反ではない。ただしサービスとして提供し続ける以上、AGPL のネットワーク条項（改変版をネットワーク越しに提供する場合のソース提供義務）が今後の改変にどう及ぶか、CLA との関係も含めて**法務・権利者への確認が必要**な別論点になる
- **CLA を結んだボランティアのコントリビューションが途絶える**。オープンであること自体がプロジェクトの信頼・ブランドの一部でもあり、これは技術判断ではなく組織判断になる

どうしても非公開の領域が必要になった場合は、リポジトリ全体ではなく「秘匿が必要な部分だけを別のプライベートリポジトリ / 環境変数 / Terraform 側に逃がす」方が筋が良い（実際、機密は既に GitHub Environments の secrets に集約されている）。

## 推奨ロードマップ

### フェーズ1: すぐできる（コード変更ほぼなし）
1. ユダさんに GitHub Write 権限 + Vercel / Supabase(staging) のアクセス付与
2. `main` / `develop` のブランチ保護を required checks + review 必須で固める
3. CodeRabbit を `assertive` に変更し、非開発者運用向けにチューニング
4. Vercel の PR Preview Deployment の有効状態を確認・有効化

### フェーズ2: Supabase Branching 導入
1. staging プロジェクトで Branching を有効化（Pro プラン確認）
2. Supabase GitHub 連携 + Vercel 連携を設定（Preview に branch credentials 自動注入）
3. 公開が必要なスキーマがあれば `config.toml` の `[api] schemas` に追記
4. PR 作成時に Preview Branch へ `mission:sync` 等を流す GitHub Actions を追加
5. PR クローズ時のブランチ自動削除を確認し、コスト管理の前提（同時ブランチ数の上限、最大稼働時間、egress の目安）を決めて Spending 監視のアラートを設定する

### フェーズ3: 運用の磨き込み
1. LINE 認証のプレビュー対応方針の決定（Email 認証フォールバック等）
2. CODEOWNERS によるパス別レビュー体制
3. 必要ならセカンド AI レビュアー（Gemini Code Assist 等）の追加
4. ユダさん向けの「PR 作成 → プレビュー確認 → マージ依頼」手順書の整備

## 確認事項（チーム / ユダさんへ）

1. 「スキーマをパブリックにしないと動かない」で想定していた**具体的なスキーマ名**は何か？（現在のマイグレーションと `config.toml` には `public` 以外の公開スキーマが見当たらないため、別プロジェクトでの経験か、ダッシュボード手動設定の可能性がある）
2. Supabase は現在 **Pro プラン以上か**？ Preview Branch の時間課金は許容範囲か？
3. Vercel で PR ブランチの Preview Deployment は現在有効か？
4. プレビュー環境で**認証込みのフロー確認がどこまで必要か**（LINE ログイン制約への対応レベルを決めるため）
5. 非公開化について: 技術的には不要という整理だが、組織方針として非公開化したい理由が他にあるか？
